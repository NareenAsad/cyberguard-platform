# Risk-Scoring Engine — Evaluation

> `.agents/data/risk_scoring_benchmark.json` to refresh this report.

## Why this evaluation looks the way it does

CyberGuard's risk score is a **deterministic weighted formula**
(`Risk = 0.30·CVSS + 0.25·Exploitability + 0.25·AssetCriticality + 0.20·ThreatIntel`,
scaled by a network-exposure multiplier), not a trained ML classifier. There is
no train/test split or held-out accuracy in the ML sense — instead this
evaluation checks two things that actually matter for a rule-based scoring
engine:

1. **Face validity** — does the formula agree with real-world/industry
   consensus severity on well-documented incidents? The benchmark set includes
   four real CVEs with known outcomes (Log4Shell, EternalBlue/WannaCry,
   Heartbleed, the Apache Struts CVE that caused the 2017 Equifax breach, and
   PrintNightmare) alongside three synthetic boundary cases designed to probe
   specific formula behavior (a HIGH/CRITICAL boundary case, the air-gapped
   exposure discount, and a LOW-severity baseline).
2. **Internal consistency (monotonicity)** — increasing any risk-increasing
   input (CVSS, exploit availability, asset criticality, active exploitation,
   network exposure) must never *decrease* the output score. A scoring engine
   that violates this would actively mislead analysts.

The same benchmark file is evaluated by **both** implementations —
`.agents/tests/test_evaluation_benchmark.py` (Python) and
`src/lib/risk_engine.benchmark.test.ts` (TypeScript) — so a green run on both
sides is also evidence the two engines agree with each other, not just with
the ground truth.

## Monotonicity checks

In addition to the labeled cases above, both test suites run parametrized
monotonicity checks confirming the score never decreases when any of the
following worsens, holding everything else constant: CVSS score, exploit
availability (`NONE → THEORETICAL → POC_ONLY → PUBLIC`), asset criticality
(`LOW → MEDIUM → HIGH → CRITICAL`), active exploitation, and network exposure
(`air-gapped → internal → internet-facing`). All checks pass on both
implementations.

## Scope and limitations

- This evaluates the **risk-scoring formula only** — it does not evaluate the
  CrewAI/Groq LLM pipeline's output quality (threat enrichment text, generated
  playbooks, executive summaries), which would require either human review or
  an LLM-as-judge setup and real API calls. The pipeline's *structural*
  reliability (does it return parseable JSON) is covered separately by
  `.agents/tests/test_json_extraction.py`.
- The benchmark set is intentionally small (8 cases) and hand-curated for face
  validity, not statistical power — it is not a substitute for a large labeled
  dataset, which does not exist for this problem (there is no public
  "ground truth risk score" dataset to train or test against).
- Threat-intel context (`active_exploitation`, `targeted_campaign`) is
  currently supplied by the caller / OTX pulse data rather than derived by the
  formula itself, so this evaluation assumes that input is accurate.
